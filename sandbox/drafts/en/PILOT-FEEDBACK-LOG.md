# English pilot feedback log

Status: four reference lessons owner-approved; source propagation implemented; full-corpus audit pending
Started: 2026-08-20

This is the append-only working record for feedback on the three English pilot lessons. It records
what the reviewer observed, what changed in the pilots, and the reusable lesson-authoring rule the
change suggests. An entry here is evidence for a future blueprint, generator, checker, or
proofreading update; it is not itself authorization to propagate the change across the curriculum.

Pilot sources:

- Core 20: `tracks/1-core-patterns/courses/core-first-exchanges-2/lessons/20-asking-for-help/lesson.html`
- Contextual 1: `tracks/2-contextual-english/courses/ctx-travel-arrivals-transport/lessons/01-check-in-and-request-a-seat/lesson.html`
- Freetalking 1 Full and its matched Accessible variant under `tracks/3-freetalking/`

## 2026-08-20 — Tutor operating clarity

### Feedback

The scripts and instructions often did not make it clear what the tutor and learner should do on
each page. The learner-facing blue script and private tutor instructions were not being used as two
distinct channels.

### Pilot changes

- Added explicit learner actions to opening, reading, controlled-practice, role-play, and transfer
  pages in Core 20 and Contextual 1.
- Added private tutor notes for role assignment, run order, pacing, answer capture, correction, and
  when to move on.
- Kept learner-facing speech out of private notes and operating detail out of learner-facing speech.

### Reusable insight

Every page needs an immediately identifiable learner action. The blue script says exactly what the
tutor says to the learner; the private note says only what the tutor must do to run that action.
Visible content is not an instruction by itself.

### Candidate propagation targets

- Core and Contextual blueprints
- English lesson-creation workflow and review checklist
- Generator templates for page scripts and tutor notes
- Proofreading checks for missing or ambiguous learner actions

## 2026-08-20 — Freetalking quality and flexibility

### Feedback

Some Freetalking questions were not interesting enough. Topic fidelity should not prevent a tutor
from following a more engaging, slightly tangential thread. A fixed sequence of related questions
can feel like an interview rather than a conversation.

### Pilot changes

- Reframed FT-1 as an eight-question pool rather than a checklist.
- Added private guidance to react, share briefly, skip freely, follow the interesting part of an
  answer, and reserve two to three minutes for feedback.
- Replaced the single-story interrogation ladder with varied conversational doorways: surprise,
  small everyday differences, explanations, visitors' misunderstandings, adaptation, and habits
  worth adopting.
- Mirrored the same intellectual jobs in the matched Accessible variant with simpler language.

### Reusable insight

Freetalking prompts should optimize for conversational value, not mechanical proximity to the
title. A coherent topic can support several angles; tutors need explicit permission to choose and
branch rather than march through every page.

### Candidate propagation targets

- Freetalking Full and Accessible blueprints
- Freetalking prompt generator and paired-variant checks
- Freetalking proofreading rubric

## 2026-08-20 — Learner reading is the default

### Feedback

The tutor should not read target language for the learner to listen and repeat unless the page is an
intentional listening exercise. In ordinary model, goal, vocabulary, pattern, and comparison pages,
the tutor should ask the learner to read the target language aloud.

### Pilot changes

- Replaced tutor-model/listen-and-repeat instructions in Core 20 and Contextual 1 with learner-read
  instructions.
- Rewrote goal pages to state the communicative goal and ask the learner to read the examples below.
- Removed the tutor-only first pass from the opening Contextual scene; the learner now reads the
  Passenger role while the tutor reads only the Agent role.
- Rewrote comparison pages so the learner reads both options before comparing them.

### Reusable insight

Do not infer a passive modeling stage merely because examples are visible. Default to learner oral
production. Tutor modeling needs a named listening or pronunciation purpose; role-play remains an
exception because the tutor is supplying the other speaker's live turn.

### Candidate propagation targets

- Core and Contextual receptive-to-productive arcs
- Goal-page, vocabulary-page, pattern-page, and native-tip templates
- Editorial search for `listen`, `repeat after me`, and tutor-read-first instructions

## 2026-08-20 — Closed choice must end in oral production

### Feedback

Choosing the correct fragment is not the complete activity. After choosing, the learner should read
the entire completed sentence aloud. The script should describe this generically so it works for any
sentence-choice content.

### Pilot changes

- Rewrote Core 20 `p1-choose` to say: choose the answer that matches the Japanese, then read the
  complete sentence aloud.
- Added a private tutor reminder to finish each row with the learner reading the entire sentence.

### Reusable insight

A closed choice checks recognition; reading the completed sentence converts that recognition into
oral retrieval. Sentence-choice instructions should name both actions without referring to the
specific nouns or scenario used by one lesson.

### Candidate propagation targets

- Core sentence-choice page template
- Generator copy for `choose-row sentence`
- Proofreading check for a missing post-choice oral step

## 2026-08-20 — Spoken answer, tutor-operated text field

### Feedback

“Fill the blank” implies that the learner should type. In the live audio lesson, the learner should
say the whole sentence, including the missing words, and the tutor should enter the answer into the
shared field.

### Pilot changes

- Renamed Core fill pages to “Say the complete sentence” and Contextual fill pages to “Say the
  complete request.”
- Rewrote the learner-facing script to require the whole spoken sentence, including the missing
  words.
- Rewrote private notes so the tutor types only the missing words exactly as spoken.
- Added private tutor-entry notes to full-sentence translation fields as well.

### Reusable insight

The visible field is shared lesson state, not proof that the learner owns the keyboard. Learner copy
states the spoken production task; private tutor copy states what to type and whether to capture only
the missing span or the full sentence.

### Candidate propagation targets

- Core and Contextual fill/translation page templates
- English input-ownership guidance
- Proofreading checks for learner-facing `fill`, `type`, `write`, or `enter` wording on spoken tasks
- Tutor-note checks that distinguish missing-span capture from full-sentence capture

## 2026-08-20 — Open production must name the pattern task

### Feedback

An open question such as “What would you ask me to help you with?” supplies a topic but does not tell
the learner what to do with the page. The script should first say that the learner will make an
original sentence using the pattern they learned, then give the specific prompt.

### Pilot changes

- Rewrote both Core 20 own-sentence pages to name the target frame, ask for an original sentence or
  answer, and then supply the event/help prompt.
- Rewrote both Contextual 1 own-request pages with the same sequence: target frame, original request,
  then the specific seat choice.
- Preserved the private tutor workflow: listen to the spoken answer, react, capture it, and add only a
  useful correction.

### Reusable insight

A question is not always an activity instruction. On a scaffolded open-production page, the spoken
script needs two parts in this order: name the learned pattern and production action, then provide the
content prompt. The wording should be reusable while the named pattern keeps the task concrete.

### Candidate propagation targets

- Core “write from scratch” page template
- Contextual own-request page template
- Generator copy for open pattern production
- Proofreading check for open pages that contain only a topical question and never name the target
  pattern or learner action

## 2026-08-20 — Goal pages orient; they do not preview the lesson

### Feedback

The three-line exchange on the Core goal page duplicated material taught later and gave the learner
an unexplained reading task before the lesson had begun. The goal page only needs to say what the
learner will be able to do and give one clear first action.

### Pilot changes

- Removed the three example boxes from the Core 20 goal page.
- Kept the spoken can-do and asked the learner to read the title aloud once.
- Added a private instruction telling the tutor to move on without teaching or correcting the title
  yet.

### Reusable insight

A goal page is orientation, not a model dialogue or diagnostic. Its spoken script should state the
can-do and give one lightweight learner action. Full examples belong on the teaching and practice
pages unless the page has an explicit listening or preview purpose.

### Candidate propagation targets

- Core goal-page blueprint and generator
- Contextual and Freetalking goal-page audit before applying the rule outside Core
- Proofreading check for goal pages that duplicate later examples or introduce unexplained tasks

## 2026-08-20 — Teaching content and activity directions need separate layers

### Feedback

The pattern-teaching box was doing two jobs in one sentence: explaining what the expression means
and instructing the learner to read the examples. The Japanese meaning block is teaching content;
the procedure for running the examples belongs in the private tutor instruction.

### Pilot changes

- Kept the blue meaning-and-use script focused on what each Core 20 pattern communicates.
- Moved “have the learner read each example aloud” into a private tutor instruction on both pattern
  teaching pages.
- Made the private procedure explicit: explain briefly, let the learner read, and do not model first.

### Reusable insight

Separate content from orchestration even when they appear on the same page. The spoken script teaches
the learner one idea; the tutor-only note says how to use the examples and who should speak. This
keeps the explanation natural and makes the classroom action unambiguous.

### Candidate propagation targets

- Core pattern-teaching blueprint and generator
- Proofreading check for scripts that combine a concept explanation with procedural directions
- Tutor-note check for teaching pages that show examples but do not say who reads them

## 2026-08-20 — Name a pattern slot by what it communicates

### Feedback

“Add the thing” identifies a noun-shaped slot but does not help the learner understand what to say.
The explanation should name the idea that belongs in the slot: what the learner needs help with.

### Pilot changes

- Replaced “the thing” on the Core request rule page with “what you need help with.”
- Updated the Japanese explanation, tutor direction, and visual formula to carry the same meaning.
- Applied the same principle to the answer rule: “what you can help with,” not “the thing.”

### Reusable insight

When teaching a pattern, label an open slot by its communicative role rather than only its grammar
category. “What you need help with” supports both comprehension and original production; “thing” or
“noun” does not.

### Candidate propagation targets

- Core pattern-rule blueprint and generator
- Proofreading check for vague slot labels such as “thing,” “word,” or “noun” when a useful semantic
  prompt is available

## 2026-08-20 — Do not repeat the task inside the response component

### Feedback

Once the blue script clearly explains the open-production task, repeating the same instruction in
Japanese at the top of the response component is unnecessary. “Spoken sentence” also describes the
medium rather than identifying whose sentence the tutor is capturing.

### Pilot changes

- Removed the duplicate Japanese task header from both Core 20 open-production response boxes.
- Changed the two pilot capture labels from “Spoken sentence” to “Student's sentence.”
- Added an opt-in `data-fb-spoken-label` hook to the shared feedback runtime so only the pilot uses
  the proposed label; every other lesson retains the current default.

### Reusable insight

Do not repeat an activity instruction in the response area when the spoken script already makes the
task clear. Field labels should identify ownership and purpose; “Student's sentence” is clearer to a
tutor than “Spoken sentence.”

### Candidate propagation targets

- Shared English feedback-component label in `shared/js/feedback.js`
- Core and Contextual blueprints that add `.fb-task` beneath an already complete script
- Rendered proofreading check for duplicate instructions above open-response fields

## 2026-08-20 — Section dividers orient; teaching starts on the next page

### Feedback

The Part 2 divider showed only a Japanese explanation of the response pattern. That made the page
look partly like a translation and partly like a teaching page, while giving the tutor no clear
procedure.

### Pilot changes

- Reworked all three Core 20 section dividers as brief bilingual transitions.
- Added a direct Japanese gloss to each section title.
- Added a private instruction to introduce the section with the one spoken line and move on; pattern
  meaning and mechanics remain on the following teaching pages.

### Reusable insight

A dark section divider is a pacing and orientation beat, not a teaching page. It should name the new
phase, give the tutor one short transition line, and explicitly defer explanation to the teaching
page that follows. A Japanese-only explanatory paragraph creates unclear content ownership.

### Candidate propagation targets

- Core section-divider blueprint and generator
- Contextual section-divider audit
- Proofreading check for Japanese-only explanations or pattern mechanics on transition pages

## 2026-08-20 — Tutor notes state the action without defensive prohibitions

### Feedback

“Do not model the sentences first” added no useful information after “have the learner read each
example aloud.” The required speaking order was already clear.

### Pilot changes

- Removed the redundant prohibition from both Core 20 pattern-teaching notes.
- Kept the actionable procedure: explain the meaning briefly, then have the learner read the
  examples aloud.

### Reusable insight

Tutor notes should state the shortest sufficient procedure. Do not add a “do not” clause when the
positive instruction already makes the intended action and speaker unambiguous. Keep prohibitions
only when they prevent a likely, consequential mistake that the positive instruction does not cover.

### Candidate propagation targets

- Core and Contextual tutor-note blueprints
- Proofreading check for redundant negative instructions after an unambiguous positive instruction

## 2026-08-20 — Role-play instructions assign visible roles explicitly

### Feedback

“Read your lines; I'll read the other part” required the learner to infer which character and color
belonged to them. The dialogue showed “Me,” “Coworker,” and green/gray bubbles, but the script did
not connect those visual signals to the speaking roles.

### Pilot changes

- Rewrote the Core 20 model-dialogue script as an explicit role-play.
- Assigned the learner to “Me” in the green speech bubbles and the tutor to the Coworker role.
- Added the same role assignment to the following completion page and clarified its top-to-bottom,
  speak-then-type procedure.

### Reusable insight

“Your lines” is clear only after roles have already been assigned. At the start of a role-play, name
the learner's visible character/color and the tutor's role explicitly, then state the speaking
action. Private notes should give turn order and capture behavior rather than asking the tutor to
infer them from the layout.

### Candidate propagation targets

- Core and Contextual dialogue/role-play blueprints
- Proofreading check for first role-play pages that use “your lines” without assigning visible roles
- Audit whether color needs to be named when speaker labels alone provide sufficient identification

## 2026-08-20 — Space editable phrases, not every line of the sentence

### Feedback

Dialogue completion sentences had excessive vertical gaps between their fixed words and the phrase
input. A prior attempt to prevent wrapped inputs from touching used `line-height: 2.7` on the whole
sentence, which inflated ordinary text rows as well as the editable row.

### Pilot changes

- Reduced dialogue completion sentence leading to a normal readable value.
- Put a small margin directly on the editable phrase input, preserving separation where it is
  actually needed.
- Kept spacing between separate dialogue turns and answer boxes unchanged.

### Reusable insight

Spacing between components and spacing inside a sentence are different problems. Use container
spacing to separate questions or turns; when an inline control needs clearance after wrapping, space
the control itself rather than increasing the line height of every word around it.

### Candidate propagation targets

- Shared dialogue-completion CSS in the next runtime release
- 360px and 480px audit of Core and Contextual decks containing `.phrase-input`
- Visual regression case for a sentence with fixed text before and after a wrapped phrase input

## 2026-08-20 — Use the visible dialogue labels instead of narrating the layout

### Feedback

The revised role-play instruction became too long by explaining the scene, color system, both role
assignments, and reading action. Once “I'll be the coworker” is stated, the visible green “Me” labels
already identify the learner's lines.

### Pilot changes

- Shortened the model page to: “I'll be the coworker. Please read the green ‘Me’ lines aloud.”
- Shortened the completion page to the same role cue plus its missing-line action.
- Removed the model page's redundant private note and reduced the completion note to the tutor's
  necessary typing instruction.

### Reusable insight

Explicit does not mean exhaustive. Assign the non-obvious role, then use stable labels already on the
page to identify the learner's action. Do not narrate scene setup or visual structure after the role
and next action are clear.

### Candidate propagation targets

- Core and Contextual role-play script templates
- Proofreading check for role-play scripts that restate both visible roles, colors, scene, and order
  after one short role cue would suffice

## 2026-08-20 — Start a role-play instead of describing a reading exercise

### Feedback

The Contextual scene opener assigned roles but then told the pair to “read the conversation from top
to bottom.” That made an airport interaction feel like a document-reading exercise rather than a
scene the learner and tutor were acting out.

### Pilot changes

- Replaced the reading-order instruction with: “Let's role-play checking in. You're the passenger;
  I'll be the agent. Let's begin.”
- Shortened the private note to tell the tutor to open with the first Agent line and keep the exchange
  moving.
- Removed the redundant prohibition against modeling the exchange first.

### Reusable insight

Contextual dialogue scripts should initiate the scene, not describe how the dialogue is laid out.
Assign the roles, name the situation, and begin. Put only the minimal pacing cue in the private note.

### Candidate propagation targets

- Contextual scene-opening and replay blueprints
- Proofreading check for role-play pages framed as “read from top to bottom”
- Audit redundant “do not model first” notes where role assignment already determines turn-taking

## 2026-08-20 — A vocabulary page must remove a real obstacle

### Feedback

The standalone “Useful expressions” page repeated two seat phrases that already appeared in the
opening scene and were taught and practiced again in the two pattern sections.

### Pilot changes

- Removed the entire “Useful expressions” page from the Contextual pilot.
- Kept both phrases in the opening scene and in the later teaching and practice pages where they
  have a clear communicative and instructional role.

### Reusable insight

A phrase can be useful without deserving its own page. A standalone expression page earns its place
only when it removes a real obstacle before the next task, teaches a meaningful contrast, or gives
the learner practice they do not receive elsewhere. Repetition alone is not enough.

### Candidate propagation targets

- Contextual lesson blueprint for expression and vocabulary pages
- Proofreading check for exact phrase duplication across scene, goal, expression, and teaching pages
- Audit other “Useful expressions” pages for a unique instructional job

## 2026-08-20 — Listening instructions must name who speaks

### Feedback

The “Understand” page told the learner to read each agent line aloud, while the tutor-only note told
the tutor to read it. That contradiction made the speaker—and therefore the activity itself—unclear.

### Pilot changes

- Reframed the page explicitly as listening: “Listen to each agent line, then choose what it means.”
- Aligned the Japanese support text with the same listen-then-choose action.
- Told the tutor to read each English agent line aloud while the learner listens and chooses.

### Reusable insight

Every listening task must assign the sound source explicitly. The learner-facing script states the
learner's action (“listen, then choose”); the private note states the tutor's action (“read each line
aloud”). Never leave the speaker to be inferred from a dialogue label.

### Candidate propagation targets

- Contextual listening-comprehension blueprint
- Proofreading check for contradictions between spoken scripts and tutor-only notes
- Audit “聞いてわかろう” pages for a clearly assigned speaker and learner response

## 2026-08-20 — One goal page, then start the scene

### Feedback

The Contextual pilot opened with a situation card that assigned the same roles and described the
same check-in task as the role-play page immediately after it. A second goal page then repeated the
lesson objective and previewed two requests that were taught later.

### Pilot changes

- Turned the opening dark page into the single lesson goal page.
- Limited it to the can-do and one lightweight action: read the lesson title aloud.
- Left role assignment and “Let's begin” on the following scene page, where those directions cause
  an immediate action.
- Removed the later duplicate goal page and its two preview examples.

### Reusable insight

A goal page orients; a scene page initiates. The goal states what the learner will practice, while
the next page assigns roles and starts the interaction. If both pages assign roles or announce the
same situation, one of them is redundant. A lesson should have one goal page, not a cover, a scene
setup, and another goal that all paraphrase one another.

### Candidate propagation targets

- Contextual opening-page blueprint and generator
- Proofreading check for multiple goal or situation-overview pages before the first teaching block
- Audit cast lists that merely repeat roles assigned on the next dialogue page

## 2026-08-20 — Do not add vague performance coaching to a simple read-aloud

### Feedback

The Contextual teaching pages mixed meaning with an instruction to read the examples, despite being
followed by dedicated read-aloud pages. One read-aloud script then told the learner to keep “the
seat clear and the ending soft,” language that was ambiguous and sounded like a physical-seat
instruction rather than useful speaking guidance.

### Pilot changes

- Kept both Contextual meaning-and-use boxes focused only on what the patterns communicate.
- Added private notes telling the tutor to explain the meaning briefly using the examples.
- Left learner production to the following read-aloud pages.
- Simplified both read-aloud scripts to “Read each request aloud,” with matching Japanese.

### Reusable insight

Only add delivery guidance when it names a concrete, teachable feature that matters to the lesson.
Words such as “clear,” “soft,” or “calm” are not useful by themselves and can create a second task.
If the activity is simply reading examples aloud, say exactly that. Teaching and production should
remain separate when consecutive pages already provide those two stages.

### Candidate propagation targets

- Contextual pattern-teaching and read-aloud blueprints
- Proofreading check for meaning explanations joined to learner procedure with “and”
- Audit vague prosody directions such as “say it clearly,” “keep it soft,” or “use a calm question”

## 2026-08-20 — Reuse approved activity scripts across tracks

### Feedback

The Contextual pilot used more elaborate instructions than the already revised Core pilot for the
same reorder and translation activities. Its rule pages also relied on abstract authoring language
such as “softener,” “request frame,” and “availability,” and its open-response boxes repeated the
task inside the answer area. The paired Freetalking pilots still carried the old three-item goal
preview and default “Spoken sentence” labels.

### Pilot changes

- Reused the Core reorder script verbatim in both Contextual pattern sections: put the words in
  order, then say the whole sentence aloud.
- Reused the Core translation script verbatim in both Contextual pattern sections: read the
  Japanese, then say it in English.
- Rewrote the two Contextual rule explanations in short, concrete language and simplified their
  tutor notes and visual labels.
- Removed the repeated Japanese task from both Contextual feedback boxes and labelled the captured
  response “Student's sentence.”
- Converted both Freetalking openings to the approved one-goal-page pattern and removed their three
  preview boxes.
- Applied “Student's sentence” to every open-response box in both Freetalking variants.
- Replaced Japanese-only Contextual part transitions with short bilingual introductions and a clear
  tutor-only move-on cue.
- Removed two leftover negative cautions from Core tutor notes where the positive next action was
  already sufficient.

### Reusable insight

An activity type should have one trusted instruction pattern across tracks unless the learner's
action genuinely differs. Track-specific content belongs in the examples, not in a more elaborate
version of “reorder,” “translate,” or “say your own sentence.” Rule explanations should name the
visible operation directly, and the answer area should capture the response rather than restating
the task.

### Candidate propagation targets

- Shared English activity-script registry for reorder, translate, fill, read, and open response
- Core, Contextual, and Freetalking blueprints and generators
- Proofreading check for divergent scripts on identical activity types
- Proofreading check for task prose inside `.fb` response components

## 2026-08-20 — Free talking may reuse the pattern, but must not be trapped by it

### Feedback

The Contextual free-talking page asked about the learner's real seat preference but forced the
answer into “We'd like ___, if possible.” That pattern is natural when making a request at a
counter, not when explaining a personal preference, so the scaffold made the conversation less
natural.

### Pilot changes

- Replaced the forced request-frame dialogue with one open question about the learner's ideal seat
  and why they like it.
- Replaced three constrained dialogue inputs with one standard student-response feedback box.
- Told the tutor to follow the most interesting detail and invite pattern reuse only when it fits
  naturally.
- Kept required target-pattern production on the earlier request, translation, and role-play pages.

### Reusable insight

Free talking is a transfer opportunity, not another exact-frame test. The topic should grow out of
the lesson, but a natural and interesting answer matters more than forcing the target pattern into a
context where a native speaker would not use it. Required pattern use belongs in controlled
production and role-play; free talking may recycle it opportunistically.

### Candidate propagation targets

- Contextual free-talking blueprint and generator
- Proofreading check for open questions paired with a compulsory target frame
- Lesson audit separating required production from optional conversational reuse

generation: a useless support page, two teaching pages with the same generic meaning, a logically

## 2026-08-20 — Retrospective: the first post-pilot sample was not actually proofread page by page

### What the owner found

- Core `p1-write` asked for a habit question without printing the required `Do you ___?` frame.
- Core `p2-fill` repeated the identical `Yes, I do` retrieval four times, so only the first row did
  any work.
- Core `p2-choose` used `do / am`, but `am` was impossible in every row. Shuffling an obviously
  wrong distractor did not create a decision.
- Core `p2-write` referred to “the same question” although no question was visible on that page.
- Core and Contextual `p3-freetalk` had been reduced to one tutor question plus a correction box;
  they were no longer reciprocal Tutor/Me conversations.
- Contextual `scene` said only “Let's begin,” without naming the action as a roleplay.
- Contextual `p1-rule` and `p2-rule` used a weaker one-example renderer instead of the approved
  visual rule component used by equivalent teaching pages.

### Why this happened

1. **The written policy existed, but the review did not follow it.** The proofreading workflow
   already required every page to earn its place, every role to be operable and Free Talk to be a
   real exchange. The review summarized titles, scripts and tutor notes instead of answering the
   page-by-page learner-decision questions on the rendered output.
2. **A structural render audit was misreported as visual approval.**
   `audit_rendered_decks.py` activated every page and measured overflow, spacing and pager
   clearance. It did not judge component consistency, communicative logic or pedagogical value.
   Only a few representative screenshots were inspected manually, but the handoff language made
   the verification sound broader than it was.
3. **A new generator branch deleted approved interaction.** In Core, adding a custom `freetalk`
   prompt selected a special branch that rendered only `feedback_compose`; it bypassed the
   existing `LIVE_SCENES` reciprocal dialogue. Contextual copied the same one-way structure. This
   was a source-level regression, not an HTML accident.
4. **The checker proved validity, not learning value.** It checked answer solvability, markup,
   target parity and speaker labels when turns existed. Zero turns also meant zero label mismatch,
   so a one-way Free Talk page passed. It never asked whether four rows repeated one answer or
   whether a distractor could ever be right.
5. **Text parity hid component drift.** Contextual rule copy was revised, but its generator still
   called `core.rule_example` rather than the approved visual `rule_page`. Reviewing extracted text
   could not reveal the design difference.
6. **Brevity was optimized without checking the referent.** “Let's begin” was short but did not say
   what was beginning. “The same question” was concise but depended on a question that was no
   longer visible. Short wording is only good when the learner's next action remains self-contained.

### Corrective process changes

- Authoring and proofreading now require every controlled row to add a real decision. An identical
  answer repeated four times or a choice with one permanently impossible option must be redesigned.
- Open production must print both the exact target frame and the concrete communicative prompt;
  cross-page references cannot carry essential instructions.
- Core and Contextual Free Talk is reciprocal by default. Pattern reuse remains optional when
  unnatural, but a one-way correction box is not Free Talk.
- The checker now rejects a Core or Contextual `p3-freetalk` page with fewer than three live turns.
- Render metrics and human visual/pedagogical inspection are recorded as separate gates. “Rendered
  successfully” may describe the former only; owner-review readiness requires the latter on every
  page.

### Status

This retrospective updates the workflow and regression guardrails. The affected sample lessons
remain a correction set and must not be treated as approved examples until their generators and
rendered pages are revised and re-reviewed.
